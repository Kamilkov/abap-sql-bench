# Text-to-ABAP-SQL test set — design

## Intent

Kamil is writing a LinkedIn article on fine-tuning a small local LLM (LoRA/MLX on a Mac mini).
The task: translate plain-English questions into **ABAP SQL** that runs on a real SAP system.
This document covers only the **test set** — the frozen benchmark every model is scored on
(base small model, fine-tuned small model, frontier baseline).

Readers are people interested in fine-tuning local LLMs, mostly **not** SAP people. They will read
the results, not reproduce them (reproducing would need an SAP A4H install). The SAP angle is the
twist: an unfamiliar SQL dialect, graded by executing against a real SAP system.

## Goals

- ~300 items, each a natural-language question with a verified reference answer.
- Questions understandable without SAP knowledge (airline/travel domain, no German, no SAP jargon).
- A difficulty spread, so the article can show *where* fine-tuning helps, not just one score.
- Every reference query proven to run on A4H, with its result stored.
- Published alongside the article: questions, reference SQL, expected results, and (later) every
  model's answers — so skeptics can inspect the work.

## Non-goals (now)

- Training data, fine-tuning, the eval harness/grader, the model-answer runs. Later phases.
- Letting readers run the benchmark themselves. No public grader; A4H is never exposed.

## Anti-goals

- **Test set written by the same model family that generates training data.** The test set is drafted
  by **OpenAI Codex** (`codex` CLI, installed), and Claude never writes or judges test items.
  Consequence for later: the article's frontier baseline is **Claude**, not GPT (GPT must not be
  scored on questions it wrote). *(Corrected 2026-10-21: this originally said training data would be
  generated with Claude; it is generated by an open-weight teacher, Qwen3-Coder-30B-A3B-Instruct —
  see `2026-10-20-training-data-finetune-design.md`.)*
- Pure LLM phrasing. Kamil reviews the survivors and rewrites stiff questions.
- Questions that only make sense to SAP insiders.
- Reference queries that "look right" but were never executed.

## Data domain

A4H, client 001, the `/DMO/` flight reference model. Allowed tables (active, transparent, non-draft):

`/DMO/AGENCY`, `/DMO/CUSTOMER`, `/DMO/CARRIER`, `/DMO/CONNECTION`, `/DMO/FLIGHT`, `/DMO/AIRPORT`,
`/DMO/TRAVEL`, `/DMO/BOOKING`, `/DMO/BOOK_SUPPL`, `/DMO/SUPPLEMENT`, `/DMO/SUPPL_TEXT`,
`/DMO/TRVL_STAT_T`, `/DMO/BOOK_STAT_T`.

Excluded: draft (`*_D`, `A_*`, `D_*`), managed-scenario copies (`*_M`), `FSA_*`, `EMPLOY*`, `ZZ_*`,
log/lock tables. The builder confirms the allowed list against actual columns/row counts and may
drop a table that is empty.

The same schema description (table + column names, types, short meaning) is given to every model
at eval time; it is stored in the repo as `schema.md` and is part of the frozen set.

## Item format

One JSON object per line in `testset.jsonl`:

| field | meaning |
|---|---|
| `id` | stable id, e.g. `q0001` |
| `tier` | `easy` \| `medium` \| `hard` \| `unanswerable` |
| `question` | English question |
| `reference_sql` | ABAP SQL (freestyle data-preview syntax); `null` for unanswerable |
| `ordered` | `true` only when the question asks for an order (top-N, "sorted by…") |
| `pipeline` | provenance of the current wording: validated + cross-checked against this exact question text |
| `expected` | captured result: column list + rows as strings; `null` for unanswerable |
| `source` | `codex` or `codex+kamil` (rewritten) |

Unanswerable items: the expected model output is the literal marker `UNANSWERABLE` *(Claude's call)*.

## Tier mix *(Claude's call, adjustable)*

- **easy ~30%** — single table, filters, sorting, simple counts.
- **medium ~35%** — joins (2–3 tables), GROUP BY aggregates.
- **hard ~25%** — subqueries, HAVING, CASE, date arithmetic, currency handling, top-N per group.
- **unanswerable ~10%** — asks for data the model doesn't have (e.g. pilot names, seat numbers, weather),
  phrased just as naturally as answerable ones.

## Pipeline

1. **Draft** — Codex generates items in batches (by tier) from `schema.md` plus a short brief.
   It writes question + reference SQL + `ordered`. Draft output kept as-is in `drafts/` for audit.
2. **Validate** — a script runs every reference query against A4H via the ADT freestyle endpoint
   (`POST /sap/bc/adt/datapreview/freestyle`, the one benchmarked at ~6 q/s). Reject: SQL error,
   0 rows, more than 1,000 rows. Flag: near-duplicate questions, identical result sets across items.
   Survivors get `expected` filled from the actual result.
3. **Cross-check** *(Kamil's decision)* — a second, independent Codex pass sees only the question and
   `schema.md` (not the draft SQL) and writes its own SQL. Both run on A4H, compared with the grading
   rules below. Agree → accepted. Disagree or second SQL fails → queued for Kamil to adjudicate
   (question, both SQLs, both results side by side). Unanswerable items: the second pass must also
   answer `UNANSWERABLE`. Claude never writes or judges reference SQL.
4. **Review** — Kamil reads survivors, rewrites stiff questions, drops weak ones. Tier balance is
   topped up with another Codex batch if needed. **Any edited question goes back through steps 2–3**
   (validate + independent cross-check against the new wording); top-up batches run the full pipeline.
   Only items whose current wording passed step 3 can be frozen.
5. **Freeze** — final `testset.jsonl` + `schema.md` committed; after that, items are never edited
   (fixes become new ids, old ones marked retired).

## Data stability

`/DMO/` data can change (regeneration shifts dates; other demos on A4H may write to it), and row counts
alone miss updates. So comparisons run in **campaigns** on one verified data state:
- **Content fingerprint:** each allowed table is read in full (ordered by primary key) via the freestyle
  endpoint and SHA-256-hashed locally; the per-table hashes are stored with the frozen set.
- **Campaign:** A4H holds no immutable snapshot and the benchmark is read-only, so identical data is
  ensured operationally, not proven by hashes:
  1. Model answers (SQL text) are generated beforehand, offline — no A4H needed for that.
  2. **Write-free window:** Kamil pauses anything that writes to `/DMO/` (e.g. Flight Rescue demos) for
     the execution phase, which is short (~1,500 queries ≈ 5 min at the measured ~6 q/s).
  3. Execution is **interleaved per item**: reference SQL and every model's SQL for an item run back to
     back, so all arms of one item see the same data within seconds.
  4. Fingerprints are taken before and after as **verification**: a mismatch invalidates the campaign.
     A match does not by itself prove nothing changed in between (a change-and-restore is invisible);
     the write-free window is what carries that.
- `reference_sql` is the source of truth; the frozen `expected` is the published snapshot for the
  fingerprint it was captured on.
- No questions relative to today ("upcoming", "this year", "last month") — use explicit dates.

## Grading rules (recorded now, implemented later)

Pass = model's SQL executes and returns the same rows as the reference:
- column names and column order ignored; **extra columns allowed** *(Claude's call)*. The grader looks
  for one **injective** mapping (each reference column → a distinct answer column) such that, after
  projecting the answer onto those columns, the **whole rows** match as a multiset (or as a sequence
  when `ordered`). Matching column-by-column independently is not allowed. Questions name what to
  return where it would otherwise be ambiguous ("list the carrier names…");
- **type-aware normalisation** using the column types in the endpoint's response metadata: character
  → trailing spaces trimmed; integers and packed/fixed decimals → **exact** decimal
  equality (formatting such as `42.40` vs `42.4` or leading zeros ignored; no rounding, so `42.4` ≠ `42`);
  floating point (e.g. ABAP SQL `AVG` without a cast returns FLTP) → equal within a relative tolerance of
  1e-9, compared only against a floating-point counterpart or a decimal of equal value; dates/times →
  ISO form. Questions that want rounding say so ("rounded to 2 decimals"). SQL NULL is represented as an explicit `null` token, distinct
  from empty string and zero;
- **ties:** any question with an order or a top-N must state a complete tie-breaker ("…cheapest first,
  then by flight date and carrier"), and the reference `ORDER BY` must end in a unique key, so the
  correct answer is deterministic. The step-3 cross-check catches items that slip through (two correct
  readings disagree → adjudication). Must hold before freeze;
- unanswerable: pass iff the model outputs `UNANSWERABLE` and no SQL.

## Constraints

- Credentials: read selectively with `node:util` `parseEnv()` (dotenv syntax, no interpolation); only
  the user/password pair is picked, nothing else enters `process.env`. Sources are tried in order;
  a source is **skipped only when neither of its two keys is present**. If either key is present, both
  must be non-empty, otherwise fail (variable names only) — never fall through to the next source.
  User and password therefore always come from the **same** source:
  1. project `.env` → `SAP_USER` / `SAP_PASSWORD`;
  2. `$HOME/.config/ai/secrets.env` → project-prefixed `ABAP_SQL_BENCH__SAP_USER` / `ABAP_SQL_BENCH__SAP_PASSWORD`;
  3. `$HOME/.config/ai/secrets.env` → unprefixed `SAP_USER` / `SAP_PASSWORD` (the existing A4H login).
  Missing or empty → fail with the variable *names* only. Never use another project's prefixed keys
  (e.g. `SUPPLY_CHAIN_RESCUE__*`). Never logged, never written to the repo.
- A4H reached via the existing SSH tunnel at `http://localhost:50000`, client 001. Read-only use only.
  Never restart the `a4h25` container.
- Code in TypeScript run natively by Node 26 (`erasableSyntaxOnly`), verified with `tsc --noEmit`.
- Freestyle preview caps rows via `rowNumber`; the validator requests 1,001 to detect the >1,000 case.

## Live endpoint findings (probed 2026-10-20, override earlier text where they conflict)

- Response is columnar XML (`dataPreview:columns` → `metadata` name/type + `dataSet/data`); errors are
  HTTP 400 with `<message>`. Seen types: `C` char, `N` numc, `D` date `YYYYMMDD`, `P` packed (incl.
  timestamps), `I`/`8` integers, `F` float (`7.5075000000000000E+03`). Numerics carry a trailing space.
- **No SQL NULL reaches the client**: the endpoint selects `INTO TABLE`, so NULLs (e.g. outer-join misses)
  arrive as type-initial values (`''`, `0.00`, `00000000`). The grader cannot distinguish NULL from
  initial; the `null` token rule is dropped, and questions must not hinge on NULL vs zero/blank.
- `dataPreview:totalRows` is **unreliable**: correct for plain and GROUP BY selects, but for an aggregate
  without GROUP BY it reports the underlying match count (`COUNT(*)` → totalRows 476, 1 row). The >1,000-row
  check therefore requests 1,001 rows and counts what comes back (as originally specified).
- The endpoint appends its own `UP TO n ROWS`; a query containing `UP TO` is rejected. The client strips
  a trailing `UP TO n ROWS [OFFSET m]` from the SQL and applies it itself (fetch n+m, drop m), so top-N
  stays expressible in normal ABAP SQL.
- Not supported by the endpoint: `WITH` (CTEs) and `UNION` (returns no rows). Supported: joins,
  subqueries, `CASE`, aggregates. These limits go into `schema.md` as dialect notes, shown to every model.
- `ORDER BY PRIMARY KEY` works for single-table reads → used for fingerprints. Largest table
  (`/DMO/FLIGHT`, 20,560 rows) reads in full in ~1.4 s.
