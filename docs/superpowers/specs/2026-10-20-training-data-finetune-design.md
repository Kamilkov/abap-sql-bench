# Training data + fine-tune — design

## Intent

Second half of Kamil's LinkedIn piece: fine-tune Qwen3-4B-Instruct-2507 to translate plain-English
questions into ABAP SQL over the `/DMO/` flight model, then show — with a test designed *before* the
results exist — whether it beats the cheap tricks. Story: "trained in the cloud, runs locally".

The objection the design must survive (Kamil's words): **"the model just memorized the test questions."**

Baseline to beat (campaign `2026-10-20-fixer3`, see `results/`): Qwen3-4B q8_0 + 3-rule syntax fixer
**52.9%** overall (easy 73 / medium 50 / hard 16 / unanswerable 94). Claude Opus 5.5 = 100% (ceiling).

## Goals

1. ~3,000 validated training pairs (question → ABAP SQL, or → `UNANSWERABLE`) generated by an
   **open-weight teacher model**, decontaminated against the frozen test set by the rules below (a
   claim about detectable overlap, not proof of separation).
2. A LoRA fine-tune of the 4B model on a rented Runpod GPU, exported to the **same runtime and
   quantisation as the baseline** (Ollama, q8_0).
3. A pre-registered evaluation: success criteria below are committed before training starts.
4. Evidence against memorization: decontamination report, similarity-bucket analysis, and a fresh test
   set written after training.

## Non-goals

- Changing `testset.jsonl`, `fingerprint.json`, `schema.md` or `prompts/answer.md` (all frozen).
- Ranking frontier models (v1 has no headroom above Claude's 100%).
- Hyper-parameter sweeps, RL, multiple base models. One base model, at most two training runs.
- Publishing the model weights (optional later, not required).

## Anti-goals

- Any test item (question or SQL) in a generator prompt, or reachable by the generator.
- A success criterion chosen after seeing results.
- Comparing the fine-tuned model under a different prompt, runtime or quantisation than the baseline.
- Spending past the budget without asking.

## Budget and time

**€35 hard cap (≈ $38), one weekend.** Estimates: Runpod GPU for teacher generation ~$2–6 and for the
fine-tune ~$3–6, Voyage embeddings < $1, Codex (fresh test set) on Kamil's subscription. Claude API
spend only for scoring Claude on the fresh test set (~50 questions, ≈ $1 — evaluation, not training)
*(Claude's call)*.
Track actual spend per step in `results/costs.md`; **stop and ask Kamil if the projected total passes
€30.**

## Part A — Training data

**Teacher — Kamil's decision: an open-weight model, not Claude.** Reason: Anthropic's terms restrict
using Claude outputs to train other models, and Kamil chose to avoid that question entirely. The teacher
must have a licence that explicitly permits using its outputs to train other models (e.g. Apache 2.0 or
MIT); **the plan's first Part A step verifies the licence on the model card and records it in this doc**.

- Default teacher *(Claude's call)*: **Qwen3-Coder-30B-A3B-Instruct** — Apache 2.0 (confirmed on the
  official model card, 2026-10-20; re-check the Qwen3-32B card if switching), strong at
  SQL, a fast MoE (3B active) that fits one 48–80 GB GPU in FP8, and from the same family as the student.
  Alternative if its yield is poor: Qwen3-32B (dense).
- Served with **vLLM** on a Runpod Pod (OpenAI-compatible endpoint, protected with `--api-key`,
  reached through the Runpod proxy). Generation and validation run from the Mac: the script calls the
  endpoint, then validates on A4H through the existing tunnel.
- Structured output via vLLM guided JSON: `{items: [{question, sql | null, tier}]}`.
- **Teacher choice is judged only on pilot yield** (share of ~300 pilot drafts that survive validation,
  cross-check and decontamination) — never on test-set scores. Switch to the alternative only if yield
  < 40%.
- The same Pod can be reused for the fine-tune afterwards (builder's call), to save setup time.

**Generator prompt contains only:** `schema.md` (dialect notes included), the live data profile
(months with flights/trips, carriers, airports, statuses — same queries as `scripts/draft.ts`), the tier
definition, the drafting rules from `prompts/draft.md` (natural business English, explicit outputs,
tie-breakers, explicit "each X" inclusion, every condition changes the answer, natural calendar
periods), and a per-request **focus** for diversity (a table combination × an SQL feature, e.g.
"bookings+customers × HAVING"). It never contains test questions, test SQL, or anything derived from
them. The generator script must not read `testset.jsonl` at all.

**Volume and mix:** ~4,500 drafted, target ≥ 3,000 kept. Tier mix like the test set: easy 30% /
medium 35% / hard 25% / unanswerable 10%.

**Validation (reuse `src/validate.ts`, `src/a4h.ts`):** `staticCheck` (incl. `foreignTables`), run on
A4H, `judge` (no error, 1–1,000 rows). Rejects are logged, not repaired.

**Label check — every pair is cross-checked** (execution alone does not prove the SQL answers the
question): a second, independent teacher call sees only `schema.md` + the question and answers with SQL
or `UNANSWERABLE`. Same rule as the test set:
- answerable pair kept only if the cross-check SQL also passes `judge` and `compareResults` matches the
  draft's result;
- unanswerable pair kept only if the cross-check also says `UNANSWERABLE`;
- anything else (disagreement, cross-check SQL error) is **unresolved and dropped** — never counted as
  evidence of unanswerability.
The cross-check is cheap on the self-hosted teacher. *(It is the same model, so it catches
inconsistency, not shared blind spots — hence the audit below.)*

**Label audit before scaling — by Kamil, not a model:** a stratified sample of **50 kept pilot pairs**
(by tier) is adjudicated by Kamil (question vs SQL vs result; correct / wrong). **Gate: ≤ 2 of 50
wrong.** Above that, fix the generator prompt and re-run the pilot before full generation. Reported as
"k/50 audited labels incorrect" — not as a population error rate.

**Decontamination — drop a training pair if any holds:**
1. word-token Jaccard ≥ 0.8 with any test question (same function as `nearDuplicates`);
2. Voyage embedding cosine ≥ a frozen threshold with any test question (`VOYAGE_API_KEY`, loaded
   selectively like `src/creds.ts`). **Calibration rule** *(Claude's call)*: pin the exact Voyage model id
   and `input_type` first. From the pilot, Kamil labels (*duplicate / paraphrase / distinct*; same task
   with different constants = paraphrase) **(a)** the 60 train↔test pairs with the highest cosine and
   **(b)** 20 random pairs from the next band down (ranks 61–300), to catch paraphrases the embedding
   ranks lower. Threshold = the lowest cosine of any pair labelled duplicate-or-paraphrase in (a) or (b),
   minus 0.01. **If none is labelled duplicate/paraphrase:** threshold = the highest cosine in (a) +
   0.01 (rule 2 then drops only pairs closer than anything seen in the pilot). Model id, labelled
   pairs and threshold are committed in a dated addendum **before** full generation and never changed
   after;
3. its result set is identical (trimmed, sorted rows) to any test item's reference result — applied
   only when the result has more than 2 cells, so coincidental single counts don't trigger it
   *(Claude's call)*.
Also drop near-duplicates *within* the training set (Jaccard ≥ 0.8, keep the first).
The decontamination step is the only code allowed to read `testset.jsonl`, and it writes only drop
decisions + a report (`results/decontamination.md`: counts per rule, cosine histogram, 10 closest
kept pairs).

**Query templates are not hidden, and that's declared.** A training pair may share an SQL *skeleton*
(constants and literals stripped, identifiers normalised) with a test item — learning the domain's query
shapes is the point of fine-tuning. Instead of hiding it, it is measured (Part C).

**Shortfall rule** *(Claude's call)*: if fewer than 3,000 pairs survive, generate more within the
budget cap; accept a final set of ≥ 2,500 rather than loosen any rule after the pilot.

**Output and dataset contract:**
- Canonical items: `train/items.jsonl` — same shape as test items (`id`, `tier`, `question`,
  `reference_sql`, `ordered`, `expected`, plus `skeleton`, `group`). Chat files are **derived** from it.
- **Grouped split** *(Claude's call)*: pairs are grouped by SQL skeleton (unanswerables by embedding
  cluster); the 95/5 train/val split is by group, so related pairs never straddle train and val.
  Outputs: `train/train.chat.jsonl`, `train/val.chat.jsonl`, `train/val.items.jsonl`.
- Each chat record uses **exactly the eval prompt** (`prompts/answer.md`, no few-shot) → assistant
  answer = SQL or `UNANSWERABLE`.
- `scripts/generate.ts` and `scripts/campaign.ts` take an **explicit `--dataset <path>`** (no default to
  `testset.jsonl`) and write answers to `answers/<dataset-name>/<model>.jsonl`; every result records the
  dataset's SHA-256. Datasets: `val` (training-side), `test-v1` (frozen), `fresh-v1` (later).
- **Enforced, not just explicit:** a committed registry pins each dataset's SHA-256 and role
  (`selection` / `test`); generation, resume and scoring refuse a mismatching hash, and refuse any
  `test`-role dataset for a fine-tuned model until the frozen-model marker (`ft-v1`) exists.
- Commit the data, generator prompts, teacher model id + vLLM version, and the generation logs.

## Part B — Fine-tune (Runpod)

- Base: Hugging Face `Qwen/Qwen3-4B-Instruct-2507` (same weights as the Ollama baseline tag).
- One on-demand Pod, single 24–48 GB GPU, stock PyTorch image. LoRA (Unsloth or TRL — builder's call),
  ~2–3 epochs. At most two runs.
- **Training objective (required):** loss on the **assistant answer tokens only** (prompt incl. schema
  masked); val loss computed the same way. Sequence length set from **measured** token lengths of the
  chat records with the Qwen tokenizer and chat template (max length + margin, no truncation). Before
  training, a check asserts that every record fits, keeps its complete answer, and ends with the
  template's end-of-turn token; the run aborts otherwise.
- **Model selection uses training-side data only** *(pre-registered)*: the epoch within a run is picked
  by val loss; between runs, by execution accuracy on `train/val.items.jsonl` run through the campaign
  grader. A second run is allowed only for a failure visible on training/val data (crash, diverging
  val loss, broken output format on val). **Neither `testset.jsonl` nor the fresh set is scored with
  any fine-tuned model until one model is frozen** (tag `ft-v1`).
- Export: merge LoRA → GGUF **q8_0** → `ollama create` on the Mac, model name
  `abap-sql-qwen3-4b-ft:q8_0`. Same Modelfile template/params as the baseline tag.
- Kamil is new to Runpod: walk him through each step; he enters his own Runpod/HF credentials.
  Artifacts (adapter + GGUF) are downloaded to the Mac before the Pod is **terminated**; a private HF
  repo push is optional.

## Part C — Evaluation (pre-registered)

**Committed before training starts** (this section is the pre-registration; do not edit it later —
additions go in a dated addendum).

- **Primary comparison:** fine-tuned Qwen, **no fixer**, vs Qwen zero-shot + 3-rule fixer, both in the
  **same campaign** on `testset.jsonl` (308 items, `compareResults` grading, unchanged prompt).
- **Primary test:** exact McNemar test, **two-sided**, on the paired pass/fail outcomes. **Success =
  two-sided p < 0.05 and fine-tuned accuracy higher.** Report the point difference and the discordant counts.
- **Secondary (reported, not decisive):** fine-tuned + fixer; per-tier accuracy (hard is the tier to
  watch); unanswerable precision/recall; SQL-error rate; Claude and shuffle control as anchors.
- **Evidence against direct copying** (wording in the article: evidence against copying, not proof
  against memorization):
  - *Seen vs unseen skeleton:* split the 308 test items by whether their reference SQL skeleton occurs
    in the training set; report fine-tuned **and** baseline (Qwen+fixer) accuracy, and the improvement,
    in each part, per tier. Report group sizes; a group (or tier cell) with fewer than 20 items is
    reported as too small to support a conclusion, and an empty group is stated as empty.
  - *Similarity buckets:* for each test item, max embedding cosine to any kept training question;
    report the **improvement over baseline** per tier × tercile (not raw accuracy, which is confounded
    with difficulty).
  - *Fresh test set:* ~50 new items drafted by Codex **after** the fine-tune is frozen, through the
    existing pipeline (draft → validate → independent cross-check → Kamil review), frozen as
    `testset-fresh-v1`. Before freezing, fresh items are screened against `train/items.jsonl` with the
    same three decontamination rules and near-copies dropped. Scored for fine-tuned, Qwen+fixer and
    Claude (≈ $1 API). Reported, not decisive (small).
- A null or negative result is published as-is.

## Constraints

- Claude never writes or judges test items; Codex drafts the fresh test set.
- `schema.md`, `prompts/answer.md`, `testset.jsonl`, `fingerprint.json` untouched; campaigns use the
  existing harness and data-stability rules (fingerprint before/after, write-free window).
- TypeScript on Node 26, `node:test`, `tsc --noEmit`, no new runtime dependencies in the repo (the vLLM
  endpoint is plain HTTP via `fetch`). Serving and training scripts on the Pod may be Python.
- Credentials loaded selectively (pattern of `src/creds.ts`); never logged or committed.
- A4H read-only via the tunnel; never restart `a4h25`.

## Addendum 2026-10-21 — teacher acceptance rules (recorded before any generation)

Kamil asked whether the pilot really shows the teacher is good enough; overall yield alone could hide a
teacher that only manages the easy tiers. Agreed with the reviewer, these practical pilot acceptance
rules (not statistical guarantees) replace the single 40% yield rule in Part A:

- `node scripts/pilot.ts` reports, **per tier**, drafted → execution-valid → cross-checked → kept after
  decontamination, with rejection reasons that separate incorrect SQL (`rejected`, `disputed`) from
  test overlap (`decontam:<rule>`).
- **Yield gate:** overall yield ≥ 40% **and** hard-tier yield ≥ 25%. Failing either → the teacher
  switch to Qwen3-32B (same pilot procedure, licence re-checked).
- **Audit gate:** 50 pairs, at least **12 hard**, at most **2 wrong overall** and at most **1 wrong
  hard**. If there are fewer surviving pairs than a tier's quota, the pilot stops; the quota is never
  silently reduced.

## Addendum 2026-10-21b — hosted open-weight teacher and an independent checker (before any generation)

Kamil asked whether a frontier model could be the teacher. OpenAI is ruled out (Codex/GPT wrote the test
set — the anti-goal in the test-set spec); Anthropic and Google API terms restrict using outputs to build
models. Instead, a larger **open-weight** model served by a pay-per-token host replaces the self-hosted
Qwen3-Coder-30B:

- **Teacher:** `deepseek/deepseek-v4-pro-0813` — MIT licence; DeepSeek's platform terms (effective
  2026-04-29) explicitly allow "training other models (such as model distillation)".
- **Cross-check:** `z-ai/glm-5.2` — MIT, a different lab, so the check no longer grades the teacher with
  itself. Qwen models are avoided as checker (student lineage), gpt-oss too (test-author family).
- Both via **OpenRouter**, pinned to **DeepInfra** (`only`, `allow_fallbacks: false`, fixed
  quantization fp8 / fp4, `require_parameters: true`, `data_collection: 'deny'`), reasoning off
  (`reasoning.effort: 'none'`), strict `json_schema` output. Prices checked 2026-10-21: DeepSeek
  $1.30 / $2.60 and GLM $0.56 / $1.80 per M tokens in / out; estimated ≈ $15 for the whole generation.
- Runpod is used only for training. `pod/serve.sh` is removed.
- Pilot rules from the 2026-10-21 addendum are unchanged, except the fallback: a failed yield or audit
  gate → one prompt-fix restart; a second failure → stop and ask Kamil (no automatic teacher switch).

## Addendum 2026-10-21c — live compliance and provenance (Gate A round 3, before any generation)

- Routing adds `zdr: true` and `enforce_distillable_text: true` (both DeepInfra endpoints are on
  OpenRouter's ZDR list, checked 2026-10-21). If OpenRouter refuses the combined policy, the run stops; the
  policy is never loosened to make it pass.
- Request settings are a wish, not proof: every response is refused unless it was served by DeepInfra, by
  the pinned model (`deepseek/deepseek-v4-pro-20260813`, `z-ai/glm-5.2-20260616`) and billed **0 reasoning
  tokens**. Every call, accepted or refused, is logged in `train/teacher-calls.jsonl` (request id, returned
  model and provider, usage, cost, settings hash).
- Saved teacher batches carry a fingerprint of their exact prompt and request settings; a mismatch refuses
  the run. Every cross-checked pair records its checker (`crosscheck_by`), and the pilot gate fails on a
  missing or mixed checker.
- The pilot counts a pair as kept only if it carries the frozen decontamination threshold; unfinished or
  undecontaminated pairs fail the gate.
- The $25 OpenRouter key limit caps API spend only; the project's €30 ask / €35 ceiling covers all costs.

## Addendum 2026-10-21d — fail closed (Gate A round 4, before any generation)

- A response without a numeric `reasoning_tokens` count is refused like one with reasoning: missing
  evidence is not compliance.
- Compliance violations and client errors (policy refusal, auth, credits, exhausted rate limit) are
  **fatal**: generation and cross-check stop dispatching, let in-flight batches finish, and exit non-zero.
  Truncated or malformed answers stay recoverable (that batch only).
- Checker provenance also covers pairs later dropped by decontamination.

## Addendum 2026-10-21e — distillation filter for the teacher only (after the first live health check)

The live health check passed for DeepSeek-V4-Pro (DeepInfra, pinned model, 0 reasoning tokens) but
OpenRouter refused GLM-5.2: "No endpoints found with models that allow text distillation" — Z.ai has not
opted GLM-5.2 into OpenRouter's distillation flag (the model itself is MIT). Kamil decided to drop
`enforce_distillable_text` **for the checker only**: the checker's SQL only votes on the teacher's label
and never becomes training data (pinned by the test "checker SQL never reaches the training export").
Zero data retention, no data collection, DeepInfra-only and all live compliance checks stay on for both;
the teacher keeps the full policy.

## Addendum 2026-10-21f — pilot 1 failed; the single permitted restart (A + B + C)

Pilot 1 (archived in `train/archive/pilot-1/`, $0.29): 64/300 agreed (21%), hard 5/70, below the yield
gate before decontamination. Causes: both models broke ABAP SQL rules (alias without `AS`, missing
blanks in function brackets, undeclared alias prefixes, FROM subqueries, date arithmetic). 57 teacher
rejections were short dumps, and syntax errors can hide semantic mistakes, so this is not "dialect only".
The checker also returned the literal string `"sql: null"` for unanswerables (28/30 disputed).
Kamil approved one restart with:

- **A. Teacher prompt:** `prompts/abap-rules.md`, an ABAP SQL rules checklist built from our own error log
  and each rule verified on A4H (nothing from the test set), inserted into `prompts/teach.md`.
- **B. Checker prompt:** "set `sql` to JSON `null` (not a string)" plus the same rules.
- **C. Frozen three-rule fixer in the training pipeline (a documented pipeline change):**
  - `src/fix.ts` is frozen (its hash, `FIXER_HASH`, is pinned by a test).
  - It is applied separately to teacher SQL (on import) and checker SQL (before execution), and never
    extended to joins, dates, subqueries or undeclared aliases: those need the prompt or rejection.
  - Raw and repaired SQL, a `repaired` flag and the fixer hash are stored. The repaired queries are
    executed and compared, and only the repaired teacher label is exported. The checker never sees
    either teacher version.
  - The fixer improves yield; it does not establish label correctness.
- **Versioning:** the teacher fingerprint covers request settings, fixer hash and the exact prompt
  (rules included). Checker provenance covers model, settings, prompt template and fixer hash.
- **Unchanged:** the frozen benchmark, the evaluation prompt, the primary comparison and every
  acceptance gate (A4H execution, independent comparison, decontamination, human audit). The pilot report
  shows repair counts per tier, and the audit sheet shows raw versus repaired SQL.
- A second completed-pilot gate failure → stop and reassess with Kamil, within the budget limits.

## Addendum 2026-10-21h — ordering by two fresh question-only judgments (approved; specified before any call)

A disclosed amendment made **after** inspecting pilot 2's failures (addendum 2026-10-21g). It replaces the
proposal in `2026-10-21-ordering-adjudication-proposal.md`, which was not adopted: there the teacher's
flag was a deciding vote, so the automated rule could not rescue any ordering dispute, and only a
pilot-only human adjudication could have.

**Rule:** the same rule applies to the pilot and to full generation, as stage `scripts/ordering.ts`,
run after the cross-check.
1. **Two fresh judgments from the question alone.** DeepSeek-V4-Pro and GLM-5.2, the existing pinned
   endpoints with all live compliance checks, each receive only `{id, question}`. They never see any SQL,
   results, the teacher's flag or a status. Each returns `ordered` | `unordered` | `ambiguous` plus the
   deciding wording (`evidence`). Prompt: `prompts/order.md`.
2. **Decision:**
   - Both `ordered` → `ordered`; both `unordered` → `unordered`.
   - Any disagreement or any `ambiguous` → the pair is **excluded** (`dropped`, reason
     `ordering:unresolved`) and counts as a loss in the yield gate.
   - The teacher's original flag is kept as `ordered_teacher` for diagnosis only. It never votes.
3. **Scope:** every answerable cross-checked pair (agreed and disputed), not just the disputes.
   Unanswerables have no order.
4. **Recompute locally:** the comparison of the teacher's result against the stored checker result is
   recomputed with the final flag. No SQL is regenerated or re-executed. Each item stores
   `ordered_teacher`, `ordered_judges` (verdict, evidence and provenance per judge), the final `ordered`
   and `ordered_reason`.
5. **No human adjudication** contributes to the yield that authorizes scaling. The 50-pair audit shows
   each pair's ordering decision and evidence, so it still checks ordering correctness.

**Unchanged:** decontamination with the frozen threshold, overall yield ≥ 40%, hard yield ≥ 25%, the
audit gate, and the hard share of training data.

**Single bounded reassessment:** pilot 2's existing pairs go through this stage, then decontamination,
then the gates. **If this pipeline fails the unchanged post-decontamination gates, the fine-tuning
experiment stops**; the procedure is not revised again. The report shows pilot 2 under the original
procedure (failed) next to the amended one.

## Addendum 2026-10-21i — audit gate failed; the fine-tuning experiment stops

Pilot 2 under the amended procedure (addendum 2026-10-21h) passed the yield gate (132/300 = 44.0%; hard
18/70 = 25.7%), but Kamil's label audit failed: **8/50 audited labels incorrect, 5/12 hard** (gate: ≤ 2
wrong, ≤ 1 wrong hard). As specified in addendum h, a failure of the unchanged post-decontamination gates
stops the fine-tuning experiment; the procedure is not revised again.

Kamil's findings:
- **7 of 8: amounts in different currencies were added or compared as one number.** Trip fees and
  flight prices are in EUR, JPY, SGD and USD; the teacher prompt already forbade this.
- **1 of 8: the SQL answers a different question** (per-carrier counts instead of an average).

**All 8 had passed A4H execution and the independent cross-check.** GLM-5.2 made the same mistake, so
execution plus two-model agreement does not catch semantic errors that both models share. That is
the main lesson of the pilot. Total API spend: $0.64. No GPU was rented.
